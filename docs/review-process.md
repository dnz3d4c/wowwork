# 번역 품질 평가 절차

게임 UI 문자열, 설명서, 설치 프로그램 문자열의 모든 번역은 이 절차를 통과해야 커밋합니다. 번역한 쪽이 "좋다"고 판단하는 것으로는 통과가 아닙니다.

## 원칙

1. **번역자와 평가자를 분리합니다.** 번역한 에이전트는 평가하지 않습니다.
2. **평가자끼리는 서로의 결과를 보지 않습니다.** 앞사람 의견에 끌려가지 않게 하기 위해서입니다. 평가 단계에는 자유 토론(Agent Teams)을 쓰지 않습니다.
3. **판정은 두 회사가 함께 합니다.** 반박된 지적은 Claude와 GPT 판정자가 각각 판정하고, 일치할 때만 확정합니다. 같은 모델은 같은 맹점을 공유하기 때문입니다.
4. **평가 구조 자체도 검증합니다.** 일부러 심은 오류를 평가자가 얼마나 잡는지 재서, 기준에 못 미치면 실제 번역에 적용하지 않습니다.
5. **지시보다 기계 검사가 우선입니다.** "하지 마라"는 프롬프트 대신, 어기면 검사에 걸리는 장치를 둡니다(용어집 검사, 판정 근거 검사, 격리 폴더, 접근 감사).
6. **한 번 되돌린 번역은 확정 용어집에 넣습니다.** 회귀 확인이나 판정에서 되돌린 번역은 다음 평가에서 다시 제안됩니다(2026-11-06 실측: "카메라 따라가기 방식"이 기록이 있는데도 두 번째로 반영될 뻔했습니다). 기록만으로는 막지 못하므로 `docs/glossary.tsv`에 올려 0단계 기계 검사가 막게 합니다.
7. **대량 작업 전에 사용자 결정을 먼저 받습니다.** 문체·용어·원문과 실제 동작이 다를 때의 처리처럼 많은 항목에 걸리는 방침은 시범 묶음에서 사용자 결정을 받아 `docs/decisions.tsv`에 적은 다음 나머지에 적용합니다(2026-11-05 실측: 설명서 "원문 충실" 결정이 51개 파일 번역 뒤에 정해져, 회귀 확인에서 위반 약 113건을 다시 고쳤습니다).
8. **koKR이 바뀌면 설명서 인용도 따라갑니다.** 반영 뒤 `uv run python -m tools.manual_sync <apply.tsv>`를 실행합니다. 같은 옛 값을 쓰는 다른 키가 있으면 영어 설명서가 어느 키를 인용하는지 보고 판단하며, 가릴 수 없으면 "판단 필요"로 보고만 합니다(2026-11-06 실측: 값이 같은 다른 키를 인용한 "제어됨" 3곳을 잘못 바꿨다가 되돌림).

## 단계

| 단계 | 누가 | 무엇을 |
|------|------|--------|
| 0. 기계 검사 | `uv run pytest -q` | 키, 서식 지정자, Lua 문법, 같은 키의 번역 일치, 확정 용어집(`docs/glossary.tsv`), 설명서 구조(제목·표·링크·코드 수). 실패하면 1단계로 넘어가지 않습니다 |
| 1. 번역 | Claude 번역자 1명 | 번역 지침 + 용어표(게임 공식 용어, koKR 번역값) |
| 2. 독립 평가 | Claude N명 + GPT N명 | 관점별로 따로, 서로의 결과를 보지 않고. 묶음에는 영어 구절을 공유하는 기존 번역(`related`)이 자동으로 붙습니다 |
| 3. 반박 | 번역자 | 지적마다 수용(수정안 확정) 또는 반박(근거) |
| 4. 판정 | Claude 판정자 1명 + GPT 판정자 1명 (서로의 결론 비공개) | 반박된 지적, 그리고 한 회사만 낸 용어 지적을 번역자가 수용한 것. 수용한 용어 지적을 판정에 넣은 까닭: 지금까지 되돌린 번역 8건 가운데 7건이 근거 확인 없이 수용한 한 회사 지적이었습니다(2026-11-08 집계: Roll Bonus, Buffered, Disabled, transit, Voice, turn in, Friends). 판정은 묶음마다 2회 호출이라 대상이 늘어도 호출 수는 같습니다. 두 판정이 일치해야 확정하고, 갈리면 사용자 판단 목록으로 넘깁니다. 번역자가 Claude라서 한 회사만 판정하면 GPT 지적이 "Claude 반박 + Claude 판정"이 되기 때문입니다(2026-11-05 실측: 그렇게 판정한 31건이 전부 기각됐고, GPT에게 다시 판정받자 7건이 갈렸습니다). 판정마다 근거 자료(`evidence_sources`)를 적어야 하고, 허용 자료가 아니면 반영하지 않고 사용자 판단 목록으로 넘깁니다 |
| 5. 회귀 확인 | 처음 보는 Claude 1명 + GPT 1명 | 수정된 항목만 다시 평가. 치명·중대 0건이어야 통과. 중대 이상 지적이 나온 항목은 그 지적을 바로 반영하지 않고 2~4단계를 다시 거칩니다(2026-11-05 실측: 회귀 지적을 바로 반영한 "카메라 따라가기 방식"이 게임 공식 메뉴 이름 "시점 전환 방식"과 달라 되돌려졌습니다). **회귀는 1회만 돌립니다.** 그 뒤에 남은 지적은 근거가 글자 그대로 확인되는 것만 반영하고 나머지는 사용자에게 넘깁니다(`docs/decisions.tsv` 2026-11-06). 1회로 줄인 근거: 2회차 회귀 7번 가운데 6번이 지적 0건, 1번이 경미 1건이었습니다(2026-11-08 집계) |
| 6. 최종 확인 | 사용자 | UI는 게임에서 직접 듣고, 설명서는 시범 묶음을 읽습니다 |

2단계에서 Claude와 GPT가 같은 항목을 지적하면(범주는 달라도 됨) 반박 없이 수용합니다. 번역자는 지적들을 반영한 최종 번역만 정합니다.

## 규칙과 근거의 출처

| 문서 | 역할 |
|------|------|
| `docs/translation-guide.md` | 번역 규칙 |
| `docs/decisions.tsv` | 사용자 결정. 날짜와 출처(사용자)가 있는 것만 적습니다. Claude가 정한 것은 여기에 적지 않습니다 |
| `docs/glossary.tsv` | 확정 용어. 0단계 기계 검사가 모든 번역에 적용합니다 |

판정 근거로 인정하는 자료는 원문, 앱 코드, 기존 번역, 게임 공식 문자열, 위 세 문서뿐입니다(`tools/review/guard.py` `ALLOWED_EVIDENCE`). UI·설치 프로그램·로그인 툴은 `tools/review/decisions.py`가, 설명서는 `manual.js`가 같은 목록으로 검사합니다(2026-11-08까지 설명서 쪽에는 검사가 없었습니다). 계획 문서, 반박문, 평가 기록은 주장일 뿐 근거가 아닙니다. 번역 쪽이 쓴 문서를 근거로 삼으면 판정이 번역자의 결정을 되받는 순환이 되기 때문입니다.

## 평가 관점

| 관점 | 무엇을 잡나 | UI·설치 프로그램 | 설명서 |
|------|-------------|------------------|--------|
| 정확성 | 뜻의 누락·추가·왜곡, `~만`·`~일 때` 같은 한정어와 조건 누락 | O | O |
| 용어 | 게임 공식 용어, koKR 번역값, 파일 간 일관성, 번역 지침의 용어 규칙 | O | O |
| 코드 맥락 | 문자열이 코드에서 어떻게 조립되고 발화되는지(이어 붙이기, 서식 순서, 선택지 라벨) | O | 실제 애드온 동작과 문자열이 설명과 맞는지 |
| 청취 | 스크린리더로 들었을 때 모호한 말과 동음이의어, 길이, 원문에 없는 기호, 문체 규칙, 말투 | O | 제목 탐색 구조는 기계 검사(`tools.manual check`) |
| 한국어 문장 | 번역투, 문체 일관성, 자연스러움 | 청취에 포함 | O |

평가자 수: 모든 대상이 관점 4개 × (Claude, GPT) = 8명입니다(`full.js`, `manual.js`의 `LENSES`). 설명서의 청취 관점(제목 탐색 구조)은 `tools.manual check`가 기계로 검사하므로 평가자를 따로 두지 않습니다.

관점 대신 페르소나(2026-11-06, 5명 × 2회사)도 시도했지만 반영 1건당 평균 3명이 겹쳐 지적했고, 그 페르소나만 잡은 반영은 92건 중 28건이었습니다. 관점 4개 체제에서는 청취 관점 하나만 잡은 반영이 81건이었습니다(2026-11-08 집계). 페르소나가 보던 말투 항목(AI가 쓴 티, 문구 종류별 말투)은 `lens-listening.md`로 옮겼습니다.

## 심각도

MQM(번역 품질 평가 업계 표준)의 세 등급을 씁니다.

- **치명**: 사용자가 잘못 행동하게 만드는 오류. 뜻 반전, 잘못된 키·숫자, 서식 지정자 오류, 다른 기능으로 오해하게 하는 용어.
- **중대**: 뜻이 일부 빠지거나 더해진 것, 공식 용어·koKR 값과 다른 용어, 들었을 때 뜻이 갈리는 표현.
- **경미**: 뜻은 맞지만 어색하거나 문체 규칙에서 벗어난 것.

## 평가 구조 검증 (오류 심기)

평가 프롬프트를 바꾸거나 새 대상(설명서, 설치 프로그램)을 시작할 때 2단계만 따로 돌려 잽니다.

1. **오류는 두 회사가 따로 심습니다.** Claude 10개, GPT 10개(`prompts/seed-generate.md`). 한 회사만 심으면 같은 회사 평가자가 유리합니다.
2. **격리 폴더에서 평가합니다.** `tools/review/sandbox.py`가 저장소 밖 임시 폴더에 오류를 심은 묶음, 오류를 심은 koKR 사본, 앱 코드, 규칙 문서, 게임 문자열만 복사합니다. 원래 번역, 정답표, 평가 기록은 들어가지 않습니다. 심을 목록과 정답표는 그 폴더 밖에 둡니다.
3. **접근을 감사합니다.** GPT는 `--events`로 실행한 명령 전체를 기록하고, Claude는 에이전트 기록이 남습니다. `tools/review/audit.py`가 격리 폴더 밖 절대 경로나 상위 폴더 이동(`..`)을 찾으면 그 검증은 무효입니다.
4. **채점합니다.** `tools/review/score.py`가 회사별, 심은 쪽별 검출률과 심지 않은 항목 지적 수를 냅니다. 어느 회사든 80% 미만이면 평가 프롬프트를 고친 뒤 다시 잽니다.

## 기록

모든 평가 결과는 `reviews/<날짜>-<대상>/` 아래 JSON으로 남깁니다. 평가자별 지적, 반박, 판정, 회귀 확인이 각각 파일 하나입니다. 이 기록이 번역 이력의 근거입니다.

## 실행

Workflow로 묶음마다 같은 구조를 결정적으로 반복합니다(2026-11-05 사용자 허용). 스크립트는 `tools/review/workflows/`에 있습니다.

| 스크립트 | 단계 | 대상 |
|----------|------|------|
| `full.js` | 2~4 | UI, 설치 프로그램(`extraPrompts: installer.md`), 로그인 툴(`logintool.md`) |
| `regression.js` | 5 | 같음 |
| `manual.js` | 1~4 | 설명서 |
| `manual-regression.js` | 5 | 설명서 |
| `guide-review.js` | 2~5 | 테스터 안내 같은 사용자 안내문 |
| `calibrate.js` | 평가 구조 검증 | 평가 프롬프트를 바꿀 때 |

GPT 평가자는 `tools/review/gpt_review.py`가 `codex exec`를 읽기 전용 샌드박스로 실행합니다. UI형 판정 결과는 `uv run python -m tools.review.decisions <출력.json> <평가 폴더>`가 근거를 검사한 뒤 반영 목록(`apply.tsv`)과 확정하지 못한 항목 목록(`escalations.json`)으로 바꿉니다. 에이전트 실패로 빠진 항목이 있으면 실패로 끝나므로 그 묶음을 다시 돌립니다.

새 키가 몇 개뿐이어도 묶음 하나에 에이전트 9~11명이 듭니다(평가 8, 번역자 1, 판정 2). 2026-11-07 V1.0.1 새 키 66개는 지적 14건, 반영 3건이었습니다.

일회성 도구(설명서 다듬기, 재처리, 사용자 결정 일괄 반영)는 2026-11-08에 지웠습니다. 필요하면 git 이력에서 꺼냅니다.
